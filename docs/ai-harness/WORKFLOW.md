# Claude Code · Codex 공통 작업 절차

프로젝트 지침의 기준은 `AGENTS.md`다. `CLAUDE.md`는 이를 불러온다.
공유 설계 지식은 `PROJECT_CONTEXT.md`(존재할 때), 코드와 기존 문서에 유지한다.
도구별 세션·자동 메모리는 참고 자료이며 작업 상태의 유일한 저장소로 사용하지 않는다.

## 시작

1. `git status --short --branch`와 현재 커밋을 확인한다. 기존 변경은 보존한다.
2. `docs/ai-harness/PROJECT.md`의 읽기 순서와 기존 진행 기록을 확인한다.
3. 관련 작업 기록에서 목표·완료 조건·남은 일을 확인하고 실제 코드와 대조한다.
4. 수정 범위에 있는 하위 `AGENTS.md`와 `PROJECT_CONTEXT.md`도 읽는다.

## 계획과 실행

- 여러 단계의 작업은 완료 조건과 검증 방법을 먼저 기록한다.
- `.planning/STATE.md`, 이슈 등 기존 상태 관리가 있으면 그것을 유지한다.
  `docs/tasks/`는 도구 전환에 필요한 작업별 인계 기록이며 동일한 로드맵을 복제하지 않는다.
- GSD가 설치된 도구에서는 기존 GSD 명령을 사용할 수 있다. 없는 도구에서는 같은 계획,
  변경, 검증 결과를 해당 Markdown 기록에 직접 남긴다. 특정 슬래시 명령의 설치를 필수로 하지 않는다.
- 기술·데이터·수식·도메인 제약과 기존 테스트 기준은 유지한다.
- 도구 전용 MCP·훅·권한·모델 설정은 각 도구에서 관리한다. 공유 절차의 실행 로직은
  저장소 명령으로 유지한다. 이 하네스는 애플리케이션의 LLM 모델이나 API 공급자를 바꾸지 않는다.

## 공통 명령

저장소 루트에서 Python 3.11+로 실행한다. 별도 패키지 설치가 필요 없다.
`python`은 현재 프로젝트의 인터프리터를 뜻한다. Windows에서 Store 별칭인 경우
`& '.\.venv\Scripts\python.exe' .harness/run.py check`처럼 실제 경로를 사용한다.

```text
python .harness/run.py doctor
python .harness/run.py status
python .harness/run.py check
python .harness/test_runner.py
python .harness/run.py commands
python .harness/run.py run test --dry-run
python .harness/run.py run test
python .harness/run.py handoff task-id --title "작업 제목"
```

- `check`: 하네스 지침 연결·문서·명령 정의 검사. 애플리케이션 테스트 통과를 의미하지 않는다.
- `test_runner.py`: 하네스 자체의 인계 파일 보존, 경로 처리, 실패 코드 전달 등을 검증한다.
- `commands`: 저장소별 실제 명령과 근거 파일, 실행 효과를 보여 준다.
- `run NAME`: 등록된 명령을 해당 작업 디렉터리에서 실행하고 실패 코드를 그대로 반환한다.
  명령이 없는 저장소는 오류를 반환한다. 테스트가 없는 상태를 통과로 표시하지 않는다.
- `handoff`: Git 상태를 담은 새 작업 기록을 만든다. 기존 파일을 덮어쓰지 않는다.
  이미 진행 중인 작업은 기존 파일을 갱신한다. 목표·완료 조건·검증·다음 행동은 작성자가 채운다.

`setup*` 명령은 의존성을 설치하고, `dev*`는 서비스를 시작하며, `build*`는 산출물을 만든다.
명령 목록을 먼저 확인하고 현재 요청에 필요한 명령만 실행한다.
기존 검사·보호 규칙을 우회하지 않는다. 계정·운영 데이터·외부 전송은 일반 검증에 포함하지 않는다.

## 도구 전환과 동시 작업

- 순차 전환: 앞 도구의 실행을 마치고 인계 기록을 갱신한 뒤 같은 작업 폴더에서 이어간다.
- 동시 작업: 작업별 브랜치와 worktree를 사용한다. 한 폴더를 두 실행자가 동시에 수정하지 않는다.
- worktree는 코드 파일을 분리한다. DB·포트·가상환경·캐시·외부 서비스가 공유되는지는 별도 확인한다.
- Git 작업을 자동 실행하지 않는다. 필요한 경로만 stage하고 변경 내용을 검토한다.
- 다른 PC에서는 커밋을 가져온 후 로컬 인터프리터와 도구 설정을 확인한다.
  저장소 설정의 갱신이 이미 열린 세션의 메모리까지 바꾸는 것으로 가정하지 않는다.

## 완료와 인계

- 목표, 완료 조건, 기준 커밋, 변경 범위, 선택 이유, 실행한 검증과 결과를 남긴다.
- 미검증 항목과 필요한 환경은 결과와 구분한다. 수행하지 않은 검증을 통과로 기록하지 않는다.
- 다음 실행자가 바로 시작할 수 있는 구체적인 다음 행동을 기록한다.
- 기존 이슈·계획·결정 문서가 있으면 링크를 남긴다. 새 설계 결정은 기존 ADR 위치를 우선한다.
- 공개 저장소 기록에는 다른 비공개 저장소의 정보나 개인 환경·인증정보를 넣지 않는다.

## 통합 작업

다른 프로젝트 기능을 사용할 때 저장소·커밋/버전·입력·출력·오류·검증 방법을 계약으로 남긴다.
실제 API/CLI/패키지 계약을 확인하기 전에는 프로젝트 이름만으로 연동 가능하다고 가정하지 않는다.
단위, 시간대, 데이터 기준일, 경로, 스키마와 외부 효과를 함께 기록한다.
